## Context

The MyST engine has various processing stages and, over time and as it developed, some confusing naming conventions came about.
For example, in MyST parlance "theme" and "template" mean roughly the same, but to the outside world "theme" has a strong aesthetic connection.
This document aims not only to capture the current status quo, but also to suggest a clarified naming scheme that can be used to standardize code and documentation.

## Pipeline steps

The MyST pipeline takes an input MyST markdown file and proceeds through the following steps:

:::{glossary}
Parse
: Take MyST markdown and produce a [myst-spec](https://mystmd.org/spec) compliant Abstract Syntax Tree (AST).
  You can see examples of these representations in the [MyST sandbox](https://mystmd.org/sandbox).

Transform
: At this stage, cross-reference resolution and other post-processing steps are performed, altering the AST.
  The various operators here are called `transformers` and include [... examples ...].

Render
: Convert one or more AST nodes into the output format.
  E.g., an HTML renderer would take an AST node and turn it into an HTML tag.

Compile
: Produce an output format from several inputs, including likely the AST.

Start
: Some output formats, such as web servers, need to be started after being compiled.
:::

## Pipeline actors

There are various actors in the pipeline that performs the above steps:

:::{glossary}
myst-cli
: The `myst` binary invoked by the user. Responsible for orchestrating the entire 
  compilation pipeline.

Transformer
: An AST pre-processor.

Extension
: A Javascript plugin that can provide roles/directives, inject AST, and/or be a transformer.

template
: As per the dictionary definition[^template-dictionary-entry], a
  template provides a pattern through which outputs are produced.  A
  template can be static (e.g., a LaTeX template from which a PDF is produced),
  or dynamic (a piece of software that produces a web app).[^theme-vs-template]
:::

[^template-dictionary-entry]: "A generic model or pattern from which other objects are based or derived." — The American Heritage, Dictionary of the English Language, 5th Edition
[^theme-vs-template]: Templates used to be known as themes, but this caused some confusion (since themes are typically related to layout and styling). In this MEP, we simply use `template` throughout.

## Actor scopes

It is important to note the scopes of (i.e., the pipeline steps performed by) of the above actors. Specifically:

1. The `myst-cli` is the orchestrator in control of the entire production pipeline.
   For convenience, it can also be used to *start* certain output formats (such as web servers).
   E.g., if the output is a web application, it can start it up.

2. Templates can vary in their complexity, and in how much of the compilation pipeline they control.
   For example, consider two output formats:

   - **PDF from LaTeX:** A *static LaTeX template* combines LaTeX
     snippets.  The `myst-cli` *renders* these snippets, and
     also invokes PDFLaTeX (with a *template* as *input*) to
     *compile* the template into a PDF.

   - **Web application:** MyST's default web output is a *web
     application*. The web application is *compiled*, by `myst-cli`,
     from a *dynamic template* (a code package). As a convenience,
     `myst-cli` will also launch the web app.

     The web application *itself* is a *renderer*.  It consumes AST
     (from a content server or `.json` file), *renders* the necessary
     React components, and then *renders* server pages,
     browsable by the user.

Actor scopes are currently vaguely defined. For example, when building
a new HTML theme, is `myst-cli` responsible for generating HTML
components, or does that happen inside the template itself? These
boundaries will be explored further over time.

## Example language

- "When upgrading the myst-spec, *renderers* are the only actors affected."

## Proposal

We propose to adopt the language from the glossaries above throughout
the code, as well as in documentation.

For example, we would rename the current `myst-theme` to `myst-webapp-template`,
and remove mentions of the word `theme` from the documentation.
